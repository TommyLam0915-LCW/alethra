# 產品缺口規格：FB-02、FB-11B、FB-10

本文件把三個尚未實作的客戶回饋條目，寫成可交付排期的產品規格。編號沿用客戶回饋包原件（FB-02、FB-11B、FB-10），不新增編號，也不把任何一項描述成已可用。

- 本文只做規格：沒有新增或修改 schema、路由、模型、資料表、套件、外部服務或 UI。
- 「現況」只描述目前程式實際會做的事；檔案與行號用於追溯，不代表行為已由瀏覽器驗收。
- 本輪不啟動 Docker、不探測 :8100、不改原 DB、不執行 migrate／seed、不 push／部署、不產生費用。
- 未實作能力一律標為「未實作」；「已有可完成的路徑」與「缺少的能力」分開寫。

追溯來源（本輪實際閱讀）：

- `backend/app/api/schemas.py`：`ALLOWED_TEMPLATES`、`StrategySpec`、`RevisionCreate`、`SupportLogCreate`。
- `backend/app/engine/backtest.py`：模板分派（三個 `run_*` 函式）。
- `backend/app/api/experiments.py`：建立、更新、修訂、執行路徑；無刪除路由。
- `backend/app/api/pilot.py`：support-logs 僅限管理員。
- `frontend/src/app/experiments/new/page.tsx`、`frontend/src/lib/copy.ts`：模板選單。
- `frontend/src/components/experiments/RevisionPanel.tsx`：修訂編輯器。

## FB-02：策略模板不足（均值回歸／區間突破／橫截面）

### 1. 使用者目標

客戶要用同一套研究流程，測試「價格偏離均值後回歸」、「突破區間後延續」、「多標的之間的相對強弱」這三類假設，而不是被迫改寫成趨勢型或固定持有型策略。

### 2. 目前可完成的路徑

- `StrategySpec.template_type` 是列舉欄位，只接受 `buy_and_hold`、`sma_crossover`、`price_change_fixed_hold`（`backend/app/api/schemas.py:20`、`ALLOWED_TEMPLATES` 於 `:8`）。研究草稿的另一個 schema 也套用同一組值（同一檔案 `:1191`、`:1227`）。
- 建立實驗的 UI 選單只列出這三個模板（`frontend/src/lib/copy.ts:183-187`；選單在 `frontend/src/app/experiments/new/page.tsx:397`）。
- 引擎只實作這三個模板的交易邏輯（`backend/app/engine/backtest.py:12-14`，分派於 `:359`、`:387`、`:415`）；未知模板在 schema 層就被拒絕，不會進到引擎。
- 三者的可表達範圍：買入持有（方向性持有）、SMA 快慢線交叉（趨勢跟隨）、固定回看期跌幅後買入並持有固定天數。它們無法表達「回到均線才出場」、「突破前 N 日高點」、「依多標的排名選股」或「配對價差」。
- `entry_rule`、`exit_rule`、`sizing_rule` 雖然是 `StrategySpec` 的欄位，但引擎不解讀它們；把規則寫進這些欄位不會產生新的交易行為。

### 3. 缺少的能力

- 均值回歸模板（SK06）：未實作。
- 區間突破模板（SK03）：未實作。
- 橫截面／配對模板（SK07／SK08）：未實作，且需要組合層級的引擎，不只是多一個訊號函式。
- 通用規則語言（讓客戶自行組合任意進出場條件）：未實作。
- 明確不在本項範圍：做空、槓桿、多標的資金分配、盤中模板。

### 4. 最小可用範圍

一次只新增一個日線模板，先把整條路徑（建立→版本→durable run→run detail→robustness）打通。建議第一個模板為 `mean_reversion_zscore`：

| 參數 | 型別與範圍 | 語意 |
| --- | --- | --- |
| `lookback_days` | 整數 5–120 | 計算均值與標準差的回看天數 |
| `entry_z` | 浮點 0.5–3.0 | 收盤 z 分數 ≤ `-entry_z` 時進場 |
| `exit_z` | 浮點 0–0.5（預設 0） | z 分數回到 ≥ `-exit_z` 時出場 |
| `max_holding_days` | 整數 1–120 | 最長持有天數，到期強制出場 |

- 僅做多、日線、next-open 執行；成本與風險參數沿用現有三個模板的處理方式。
- 訊號只用當日及之前的收盤資料，不得使用未來資料。
- 若 owner 選擇先做區間突破，則以「前 N 日高點突破進場、前 M 日低點或固定持有天數出場」為等價的最小規格，參數名稱與範圍需在實作前定稿。

### 5. API／schema／權限影響

- `ALLOWED_TEMPLATES` 與 `StrategySpec.template_type` 的正則需同步擴充；研究草稿的兩個驗證器也要一起更新，避免同一份規格在不同入口得到不同結果。
- 引擎新增一個 `run_*` 函式與分派分支；`backend/app/services/robustness.py` 的 `_required_bars` 需加入新模板的最少資料需求。
- 前端：模板選單、對應參數輸入、修訂編輯器（`RevisionPanel.tsx`）需支援新模板；run detail 的 captured parameters 為通用顯示，不需改結構。
- 無新資料表（策略規格仍是 JSON）、無 migration、無新套件、無新資料供應商、無權限變更（仍以實驗擁有者為界）。
- 測試：新模板的進出場、無前視、資料不足拒絕、config_hash 穩定性、既有三個模板回歸。

### 6. 驗收條件

1. 客戶可在「新建實驗」選到新模板、輸入參數、建立版本，並跑出一筆 durable run（`POST /api/v1/versions/{version_id}/runs`），run detail 顯示該次 run 實際記錄的參數。
2. 同一份 spec、同一份資料重跑，`config_hash` 與交易序列一致（可重現）。
3. 未知模板仍被 schema 拒絕，不能藉由 `entry_rule` 等未解讀欄位繞過。
4. 原有三個模板的行為與既有測試不變。
5. robustness 計畫對新模板計算的最少 bars 正確；資料不足時明確拒絕，不以模擬數字補足。
6. 僅使用既有資料來源（demo 或已核准的 OHLCV provider），不新增外部資料服務。

### 7. 待決事項

- 第一個模板選均值回歸還是區間突破（建議均值回歸，參數量少且與現有引擎差異清楚）。
- 參數名稱與範圍是否照上表定稿。
- 是否僅做多；出場優先序（訊號先於最長持有天數）。
- 新模板是否同日開放於修訂編輯器，或先只開放新建實驗。
- 與 FB-11B 的先後次序（若先做模板目錄，客戶可更早知道可用參數）。

## FB-11B：策略作為一級物件、版本化與批量匯入

### 1. 使用者目標

把一套已驗證的規則，重複用在多個標的與多個時間窗，保留版本譜系，並在不建立實驗的前提下先檢查規格是否可用。

### 2. 目前可完成的路徑

- 策略目前內嵌在每個實驗版本：建立實驗時必須一起送出完整 `strategy_spec`（`ExperimentCreate.strategy_spec` 為必填）。
- 修改策略參數會產生新版本：`PUT /api/v1/experiments/{experiment_id}` 帶 `strategy_spec` 與 `change_reason`（`backend/app/api/experiments.py:212-253`）。
- 更完整的修訂路徑為 `POST /api/v1/experiments/{experiment_id}/revisions`（`:390` 起），要求 `base_version_id`、`strategy_spec`、`change_reason`；內容與來源相同或與既有版本重複時會被拒絕。
- 執行綁定版本所屬的實驗：`POST /api/v1/versions/{version_id}/runs`；ad-hoc 回測也需要既有版本。
- 跨實驗重用：目前只能重新提交同一份 JSON，形成新實驗與新血緣；沒有「引用既有策略版本」的路徑。實驗沒有刪除路由（所有 `@router.delete` 中不含 experiments），建錯只能保留或改標題／狀態。
- 預檢：`StrategySpec` 只在建立／更新／修訂請求內驗證；沒有獨立的 validate 或 dry-run 端點。
- 模板目錄：沒有列出模板與其參數鍵／語意的端點（後端路由中無 templates 路由）。

### 3. 缺少的能力

- 策略一級物件與跨實驗的版本譜系：未實作。
- 模板目錄（參數鍵、範圍、語意、哪些欄位真的被引擎解讀）：未實作。
- 不建立物件的提交預檢：未實作。
- 批量匯入與批量預檢：未實作。
- 跨實驗引用同一策略版本：未實作。

### 4. 最小可用範圍

分兩階段；本輪只把第一階段寫成可排期規格。

第一階段（只讀、不寫入、無 migration）：

- `GET /api/v1/strategy-templates`：回傳三個模板的中繼資料，至少包含 `template_type`、顯示名稱、必要與選用 `signal_parameters` 鍵、每個鍵的型別與範圍、哪些欄位會被引擎解讀、哪些只是儲存、目前引擎版本。
- `POST /api/v1/strategy-specs/validate`：請求本文為 `StrategySpec`；回傳 `valid`、正規化後的 spec、`config_hash`、逐欄錯誤；不建立任何資料列。
- 呼叫者為已登入客戶；無需管理員權限；不呼叫外部服務；結果決定性。

第二階段（需 owner 明確批准，含 migration 與權限模型變更）：

- 新增策略與策略版本實體，實驗版本引用策略版本；定義擁有者、是否可分享、版本不可變、與 locked／retired 狀態的關係。
- 批量匯入以 JSON 陣列為格式（不使用外部服務），先預檢再匯入。

### 5. API／schema／權限影響

- 第一階段：新增唯讀路由，重用既有 `StrategySpec`；不新增資料表、migration、套件或供應商；不改既有建立／修訂／執行行為；權限仍為一般登入客戶。若加上率限制，沿用既有 limiter，不另建機制。
- 第二階段：新增資料表與 additive migration；實驗版本增加外部鍵；需要重新檢視擁有權與跨使用者可見性；批量匯入需要大小上限與逐筆錯誤回報。
- 兩階段都不得讓客戶以本文欄位指定他人 `user_id` 或存取他人策略。

### 6. 驗收條件（第一階段）

1. 客戶可在不建立實驗的情況下，列出模板並看到參數鍵、範圍與語意；內容與引擎實際接受範圍一致（以同一份程式常數為來源，避免文件漂移）。
2. 合法 spec 經 validate 回傳的 `config_hash`，與建立版本或 run 時實際儲存的 hash 相同。
3. validate 前後資料列計數不變（無寫入副作用）。
4. 非法 spec 回傳明確的逐欄錯誤；不洩漏堆疊、SQL 或連線資訊。
5. 未登入回 401；其他使用者的資料不受影響。
6. 既有建立、修訂、執行與比較行為不變（回歸）。

### 7. 待決事項

- 第一階段是否已足以回答 FB-11A（若是，FB-11B 可降為體驗需求）。
- 是否需要真正的一級物件（成本：migration、擁有權、分享規則）。
- 分享範圍：僅本人，或可團隊共用。
- 批量匯入格式與上限；版本是否永久不可變；與 locked／retired 的互動規則。
- 模板目錄的資料來源放在程式常數還是資料庫（前者簡單但需同步部署，後者可即時調整但要多一層）。

## FB-10：站內客戶回饋入口

### 1. 使用者目標

客戶遇到問題或有建議時，能在產品內直接提交，並在產品內看到自己送出內容的狀態，不必離開產品或依賴 owner 轉交。

### 2. 目前可完成的路徑

- 站內沒有客戶回饋入口。
- `POST /api/v1/pilot/support-logs` 存在，但僅限管理員（`require_admin`，`backend/app/api/pilot.py:312-316`），且 `SupportLogCreate` 要求呼叫者提供 `user_id` 與 `time_spent_minutes`（`backend/app/api/schemas.py:1049` 起）。這是營運側的工時與支援紀錄，不是客戶回饋通道；用它寫入會把客戶資料放進營運命名空間，因此未使用。
- 前端沒有任何回饋或支援提交表單；管理頁的「支援請求」是營運漏斗統計，不是客戶入口。
- 因此客戶回饋包本身也只能由 owner 轉交，形成自我指涉的閉環缺口。

### 3. 缺少的能力

- 客戶可用的提交端點與介面：未實作。
- 草稿狀態與「未提交」標示：未實作。
- 客戶檢視自己回饋與狀態：未實作。
- 營運分流與狀態轉換：未實作（現有 support-logs 不對應客戶語意）。
- 由草稿產生的匯出／下載標示「未提交」：未實作。

### 4. 最小可用範圍

- `POST /api/v1/feedback`：類別（`bug`／`usability`／`data_issue`／`feature_request`／`other`）、主旨（1–200 字）、內容（1–5000 字）、可選頁面路徑（≤200 字）、可選應用版本（≤50 字）、可選關聯對象（限呼叫者自己的實驗／run／版本）。`user_id` 由 token 決定，本文不得指定。
- `GET /api/v1/feedback/mine`：列出自己的回饋與狀態（`submitted` → `triaged`／`closed`）及時間。
- 管理端（沿用既有管理命名空間或新增管理路由）：列出與轉換狀態；一般客戶不可見他人回饋。
- 前端：登入後頁面提供固定入口；送出前後明確區分「草稿／未提交」與「已提交」；由草稿產生的匯出或下載必須標示「未提交」，不得呈現成已送達。
- 最小版明確不含：附件或圖片上傳、email／Slack／webhook 等外部投遞、外部工單系統串接、客戶可見的營運回覆。這些需要額外的儲存、掃描或外部服務，另案決定。

### 5. API／schema／權限影響

- 新增回饋資料表與 additive migration；新增客戶路由與管理路由。
- 權限：客戶只能建立與讀取自己的回饋；管理員可讀取與轉狀態；不得以本文欄位冒充他人。
- 率限制沿用既有 limiter（例如每使用者每小時上限），回 429 並附原因。
- 無新套件、無外部服務、不寄送郵件、不上傳檔案。
- 不重用 `support_logs` 的營運欄位（`time_spent_minutes` 等）作為客戶必填欄位；是否共用資料表由 owner 決定（建議新表）。

### 6. 驗收條件

1. 客戶從介面提交後，「我的回饋」可看到同一筆，狀態為 `submitted`；重新載入或自動刷新後仍存在，不需手動重整資料庫。
2. 請求本文中的 `user_id` 被忽略或拒絕；無法查詢或提交成他人的回饋（跨使用者測試）。
3. 草稿在提交成功前明確標示「未提交」；由草稿產生的匯出／下載同樣標示「未提交」。
4. 未登入回 401；超過率限制回 429 並說明原因。
5. 管理員可看到並轉換狀態；一般客戶看不到他人回饋。
6. 整個流程不呼叫外部服務、不寄送郵件、不上傳附件（本版）。
7. 既有 pilot／support-logs 的營運行為不變（回歸）。

### 7. 待決事項

- 使用新資料表，或在既有 support-logs 加上來源欄位（建議新表，避免污染營運指標）。
- 保留期限、客戶能否撤回或刪除自己的回饋。
- 是否納入附件（需要儲存與掃描，建議延後）。
- 是否顯示營運回覆（第一版建議只顯示狀態）。
- 分流責任人、狀態定義與回應時限。

## 共通交付邊界

- 以上三項目前皆為「規格已寫、功能未實作」；不得在對客戶的說明中寫成已可用。
- 實作時不得順帶新增未核准的資料供應商、外部服務、套件或權限模型變更；FB-11B 第二階段與 FB-10 的附件／外部投遞需另行批准。
- 任何新能力都必須有對應的離線測試與（可行時）瀏覽器驗收；只有 OpenAPI 描述或文件存在，不算行為已驗證。
