## 1. FB-21 v2：一份 study = 一個授權單位（採你方建議 (b)）

### 1.1 語意

- `max_attempts` 仍是**上限**，不是可扣減的授權數。
- 一份 study 無論 plan 內有幾個 cell，開始執行時只扣 **1** 個 `research_run` 授權。
- 收費時機：第一次 `POST /api/v1/robustness/{study_id}/run` 時以 CAS 方式 claim（`authorization_reservation_id IS NULL` 才寫入）；study 內所有 cell 共用該 reservation。
- 已開始的 study 續跑（部分 cell 未完成）不再收費。
- 若一個 cell 都未曾執行就被拒絕／取消，reservation 會 release 並清空 claim。
- 同一 study 已有 `reserved` reservation 時，第二次 run 回 **409 `study_running`**，不會產生第二筆扣額。

## 2. FB-24：429 指向「可執行」的那一個 GET

`POST /api/v1/robustness/{study_id}/run` 在額度不足時回 429，detail 內含：

```json
{
  "error": "insufficient_quota",
  "quota_type": "research_run",
  "unit": "study",
  "required": 1,
  "estimated_attempts": 9,
  "remaining": 0,
  "used": 5,
  "limit": 5,
  "source": "<entitlement source>",
  "check_url": "/api/v1/usage/quota?quota_type=research_run_limit&period=monthly",
  "message": "This study needs 1 research-run authorization for its 9 backtests, and 0 remain, so the study did not start. The whole study is one unit; it is not charged per backtest. Check used versus limit at GET /api/v1/usage/quota?quota_type=research_run_limit&period=monthly."
}
```

- 指引的是你方已驗證有數字的 `GET /api/v1/usage/quota?quota_type=research_run_limit&period=monthly`，不是空白的 Plans 頁。
- `GET /plans` 仍回 `{plans: []}`、`GET /usage/summary` 仍無 quota 欄位；本輪**沒有**改這兩個契約。是否把 quota 併入 `/usage/summary` 屬於契約變更，需 owner 決定，本輪不擅自改。

## 4. 第 5 節 ①：正式 warm-up 規則

新欄位 `plan.required_bars_rule`，與 `plan.required_bars`（數字）同源：

| template | 規則 |
|---|---|
| `sma_crossover` | `long_window + 1` bars（訊號引擎在 index `long_window + 1` 才可能出現第一次交叉） |
| `price_change_fixed_hold` | `lookback_days + min(holding_days, 5) + 1` bars（規劃規則最多計 5 個持有日，較長持有期可能在 slice 末端仍未平倉） |
| 其他 | 3 bars（引擎對未宣告數值預熱的模板之下限） |

邊界說明：這個規則是 **planning 用的每 slice 最少 bar 數**，用來拒絕過短的 slice；它不是我方在回測引擎內另外做「減去 warm-up」的處理，回測仍使用 slice 內全部可用 bars。若你要引擎層也輸出同樣的 warm-up 宣告，屬另一個介面變更，本輪未做。

## 5. 第 5 節 ④：portfolio `total_unrealized_pnl: null` 時讀哪一本帳

兩本帳不是同一本，不能互相代填：

1. **portfolio 帳**：`GET /api/v1/paper-portfolio/{portfolio_id}`（含 open positions 的標記估值）。
   - portfolio 綁定 replay session 時，用該 session **已儲存的 bars、截至 session cursor** 估值，`valuation.mode="session_replay"`。
   - 未綁定 session 時才用 demo fixture，`valuation.mode="synthetic_fixture"`、`valuation.price_source="demo_synthetic_fixture"`。
2. **session 帳**：`paper_equity` 是該 session 在自己 cursor 的權益。

`total_unrealized_pnl` 為 `null` 的條件是：**至少一個 open position 在 marks 中找不到 bar**。此時：

- 不會用 `0` 代替；
- `valuation.unpriced_assets` 列出缺價的 asset；
- `valuation.data_as_of` 是實際用到的 bar 日期集合。

讀法：先看 `valuation.mode` / `price_source` / `unpriced_assets`。`unpriced_assets` 非空時，這是資料缺口，不是「沒有盈虧」；不要拿 session 的 `paper_equity` 去補 portfolio 的 P&L，因為兩者的持倉與訂單集合可以不同。

本輪未在 :8100 重驗此路徑（runtime 未運行）；以上為源碼語義（`backend/app/api/paper_portfolio.py:325`、`:340–371`）。

## 6. 第 5 節 ⑤：journal 的 `closed` 語義

`record_classification` 的定義（`backend/app/api/paper_portfolio.py:1260`、`:1337`）：

- `closed`：**該筆 order 已到達終態**（filled／cancelled／rejected）。
- `open`：**該筆 order 仍是 pending**。

它不是「position 已平倉」、不是「portfolio 已退休」、也不是「journal 已凍結」。所以一筆 cancelled／rejected 的 order 會顯示 `closed` 而完全沒有出場成交，這是正常語義。

本輪未重跑 journal 測試；語義取自上述 source 與既有測試檔 `backend/tests/test_manual_decision_books_linked_portfolio.py`、`backend/tests/test_paper_journal_csv_export.py`（本輪未執行）。
