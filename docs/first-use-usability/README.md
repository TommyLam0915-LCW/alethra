# 首次使用可用性測試包（C 輪）

**狀態：未執行（NOT RUN）。** 到目前為止沒有任何真實、未參與開發的受試者。本目錄只有工程走查紀錄與測試材料；沒有訪談逐字稿、沒有成功率、沒有滿意度分數。任何日後的結果欄位，只有在真實受試者完成後才可填寫。

## 這個測試想回答什麼

一位有投資研究習慣、但沒有參與開發的人，在不接受逐步指示的情況下，能否：

1. 知道自己現在處於什麼狀態；
2. 知道下一步是什麼，而且下一步真的可以操作；
3. 不需要 UUID、資料庫或工程指令；
4. 不會把「訓練模型」誤當成唯一有價值的工作；
5. 在資料不足時不會看到假進度；
6. 不會被預先勾選的同意誘導。

工程走查（自動化、Playwright、API）只能證明系統行為；**不能**代替真人觀察。兩者的結論必須分開寫。

## 工程走查（已完成；不是使用者測試）

2026-10-29 在候選環境（前端 3100、後端 8100、disposable 資料庫 `alethra_personal_e2e_candidate_20261029`）完成：

- 三個狀態（空白、資料不足、已訓練）以真實登入讀取：空白帳號只有入口與說明；資料不足帳號有 1 個已鎖定策略版本、5 筆決策（3 筆已確認）、無同意；已訓練帳號有 205 筆已確認決策、1 個有效同意、2 個模型版本、下一個步驟為執行推論。
- 異常路徑：worker 離線、心跳過期、訓練失敗、慢回應、提交後重新整理、手機操作。詳細結果見本輪最終報告。
- 任務 B 的完整流程（建立實驗 → 回測 → 修訂 → 回測 → 比較 → 重新載入）以既有 tracked Playwright 規格在候選環境跑通：6/6。
- 四項 tracked 首次使用回歸：4/4。包括以 route fixture 驗證「只未達較嚴格品質門檻」不再被寫成「已拒絕訓練」；空白與資料不足帳號仍顯示「不符合（見下方原因）」，因為它們有真正的硬性阻礙（未有決策／未有同意）。
- 走查期間發現並修正了一個狀態錯誤：已訓練帳號明明有 2 個模型版本，資格徽章卻寫「不符合（已拒絕訓練）」。原因是資格檢查（較嚴格品質門檻）與建立快照的實際閘門（同意範圍、已確認決策數、可用資料）不是同一件事。修正只改措辭與說明，不改變任何訓練閘門；並以 tracked regression 覆蓋。
